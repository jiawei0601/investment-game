# M3 保證金引擎（本版最大工程）

## 目標

實作台指期口數撮合、逐日洗價、追繳、盤中強平、結算日轉倉、交易成本、現金流，全部觸價與強平判定只認 M2 產出的生成日內層資料，逐日結算認真實日K。這是 v2.0 相對 v1.0 新增且最複雜的模組（SPEC §4、§10、ADR 0007）。

## 依賴

M2（需要生成日內引擎提供觸價與強平判定用的真相層資料）。

## 驗收條件

- [ ] 口數撮合：買 / 賣 / 反手皆以口數為單位（大台/小台/微台三種契約可混用同一部位），乘數分別為 NT$200 / NT$50 / NT$10；需有測試驗證混合口數下的權益數計算正確
- [ ] **觸價判定只認生成日內層**：停損、限價單觸發、盤中維持保證金檢查皆以 M2 生成的日內路徑逐段計算，需有測試證明撮合模組不讀取、不呼叫任何真實日K以外或生成日內層以外的價格來源（互鎖見 SPEC §9-1、§9-5）
- [ ] **逐日結算認真實日K**：每日收盤後按真實日K收盤（結算價）逐日洗價，更新權益數；需有測試區分「盤中判定用生成日內」與「逐日結算用真實日K」兩條路徑不互相污染
- [ ] 保證金近似制：原始保證金 ≈ 指數 × 乘數 × 0.10、維持保證金 ≈ 原始 × 0.75，隨指數水準浮動；需有單元測試驗證不同指數水準下的保證金金額正確
- [ ] 追繳：權益數低於維持保證金 → 產生追繳通知，次日開盤前未補足 → 觸發強制砍倉；需有測試涵蓋「權益跌破維持保證金 → 次日追繳」與「次日補足 → 解除追繳」兩種案例
- [ ] 盤中強平：權益數（依生成日內路徑逐段計算）跌破維持保證金且無可用資金 → 依序強制平倉；需有測試案例明確定義同一時刻多部位時的強平順序（例如虧損最大者優先，或依開倉時間），並驗證強平發生在生成路徑內的正確時間點
- [ ] 結算日自動轉倉：每月第三個週三，近月部位自動轉倉為次近月，成本＝固定滑價（1-2 點，可設定）＋手續費；玩家可選擇改為平倉；需有測試驗證轉倉發生在正確結算日且成本正確扣除
- [ ] 交易成本：手續費（大台/小台/微台各檔位，開局可自訂，附常見價目預設）＋期交稅（契約價值 × 十萬分之二），需有測試驗證扣除金額正確
- [ ] 現金流：每月固定投入（模擬薪水）正確累加進帳戶；整局最多觸發一次重大衝擊事件（如「兩週內必須提出 30 萬」），需有測試驗證同一局不會觸發第二次，且觸發時機偏好帳面虧損最大時（可用加權抽樣，測試驗證此偏好方向成立而非均勻隨機觸發）
- [ ] 強迫砍倉時記錄「砍的是哪個部位、當時帳面賺賠」，供 M4 行為系統讀取作為診斷資料
- [ ] 起始資金為玩家開局輸入的真實金額量級，帳務計算以此為基礎，不可用固定假資金覆蓋玩家輸入
- [ ] 全部帳務邏輯有獨立單元測試，不需要 UI 即可跑

## 建議派工模型

`sonnet` 起跳，關鍵演算法（盤中強平順序邏輯、逐日洗價與生成日內判定的資料流隔離）建議完成後交 `opus` 複核一輪——這是本版工程量最大、也是唯一真相層互鎖（SPEC §9-1、§9-5）最容易被破壞的模組，一旦強平判定意外讀到錯誤價格來源，整套訓練機制的公正性就崩潰，複核成本遠低於事後排查代價。
